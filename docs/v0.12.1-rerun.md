# zsasa 0.12.1 benchmark rerun

The manuscript benchmarks are measured again with `zsasa` 0.12.1. Comparators keep
their pinned builds. They are rerun in the same session wherever a manuscript
headline compares against them, so those speedups come from one session.

## Scope

| Area | Manifest | Run id | zsasa | Comparators in this session | Retained comparator rows |
| --- | --- | --- | --- | --- | --- |
| Static validation | `validation-ecoli-zsasa-0.12.toml` | `v0_12_1_validation` | full grid | FreeSASA | none |
| Trajectory validation | `validation-md-5wvo-zsasa-0.12.toml` | `v0_12_1_validation` | full grid | MDTraj (per frame) | none |
| E. coli PDB batch | `batch-ecoli-zsasa-0.12.toml` | `v0_12_1_batch` | 1/4/8/10/20/40 threads | FreeSASA batch, RustSASA, Lahuta at 1/4/8/10 | none |
| Human PDB batch | `batch-human-zsasa-0.12.toml` | `v0_12_1_batch` | 10/20/40 threads | FreeSASA batch, RustSASA, Lahuta at 10 | none |
| Human mmCIF batch | `batch-human-cif-zsasa-0.12.toml` | `v0_12_1_human_cif` | parser x input I/O x 10/20/40 | Lahuta bitmask at 10 | none |
| SwissProt batch, passive I/O | `batch-swissprot-passive-io-zsasa-0.12.toml` | `v0_12_1_swissprot_passive_io` | f32 standard/bitmask at 10/20/40, one run each | Lahuta bitmask at 10 | none |

| Trajectory throughput | `trajectory-128-zsasa-0.12.toml` | `v0_12_1_md_128` | native 10/20/40, Python integrations at 10 | MDTraj, mdsasa-bolt on 5wvo and 6sup | mdsasa-bolt on 5vz0 (`v0_9_0_md_128`) |

The AFDB dimer demonstration is not rerun; the manuscript states the commit it used.

Since 0.9.0, `zsasa` leaves HETATM records and water out by default. None of the
benchmark inputs is affected: the AFDB collections have neither, the single-file
inputs were checked with the 0.12.1 build (all sixteen PDB and mmCIF inputs give
the expected atom counts), and the trajectory topologies are protein-only.

## Before running

- Pin: the `zsasa_0_12_1` flake input, the `zsasa-0.12.1` wrapper and the uv source
  for the Python package all point at the `v0.12.1` tag.
- Check that the tools resolve: `nix develop -c uv run python scripts/check_tools.py --profile rerun_0_12_1`.
- Leave the machine idle: no other work, no tool calls from an agent session while
  a timing runs. Interactive use cost 9% on Lahuta and up to 35% on a warm 10-thread run.
- Pass `--run-id` explicitly. The runners do not read the manifests'
  `run_id_default`; without `--run-id` they write under `v0_6_0_full`.

## Order and commands

Run inside `nix develop`. Times are estimates from the 0.9.0 session.

```bash
D=config/datasets.local.toml

# 1. Validation (about 30 min, not timed)
uv run python scripts/run_validation.py --manifest manifests/validation-ecoli-zsasa-0.12.toml --datasets $D --run-id v0_12_1_validation --execute
uv run python scripts/run_trajectory_validation.py --manifest manifests/validation-md-5wvo-zsasa-0.12.toml --datasets $D --run-id v0_12_1_validation --execute

# 2. PDB batch (about 1 h 15 min)
uv run python scripts/run_batch.py --manifest manifests/batch-ecoli-zsasa-0.12.toml --datasets $D --run-id v0_12_1_batch --execute
uv run python scripts/run_batch.py --manifest manifests/batch-human-zsasa-0.12.toml --datasets $D --run-id v0_12_1_batch --execute

# 3. Human mmCIF batch (about 15 min)
uv run python scripts/run_batch.py --manifest manifests/batch-human-cif-zsasa-0.12.toml --datasets $D --run-id v0_12_1_human_cif --execute

# 4. Single file (about 45 min)
uv run python scripts/run_single_file.py --manifest manifests/single-file-sample-zsasa-0.12.toml --datasets $D --run-id v0_12_1_single_pdb --execute
uv run python scripts/run_single_file.py --manifest manifests/single-file-mmcif-sample-zsasa-0.12.toml --datasets $D --run-id v0_12_1_single_mmcif --execute

# 5. Trajectory (about 4 h)
uv run python scripts/run_trajectory.py --manifest manifests/trajectory-128-zsasa-0.12.toml --datasets $D --run-id v0_12_1_md_128 --execute

# 6. SwissProt under the passive policy (about 1 h 30 min; last, its files evict the cache)
uv run python scripts/run_batch.py --manifest manifests/batch-swissprot-passive-io-zsasa-0.12.toml --datasets $D --run-id v0_12_1_swissprot_passive_io --execute
```

Do not stop a runner while hyperfine is running: the hyperfine JSON stays empty
when its stdout pipe closes.

## After running

Import each run id into `results/benchmark.duckdb`:

```bash
for r in v0_12_1_validation v0_12_1_batch v0_12_1_human_cif v0_12_1_single_pdb \
         v0_12_1_single_mmcif v0_12_1_md_128 v0_12_1_swissprot_passive_io; do
  uv run python scripts/import_full_rerun.py --run-id $r --datasets config/datasets.local.toml
done
```

Then regenerate the tables (`scripts/export_summary_tables.py`) and the figures
(`docs/figure-inventory.md`).

## Outcome

The full run took 7 h 20 min on 2026-10-29/30 and every step finished.

`scripts/benchlib/reporting.py` selects what the reports use. `CURRENT_ZSASA` and
`MD_RUN_SET` name the 0.12.1 release and its trajectory run set, `_ADOPTED` lists
the run sets per benchmark kind, and `retained_for_reporting` keeps only the
comparator rows of earlier sessions listed in the scope table above. The
0.9.0 and 0.11.0 run sets for E. coli, Human, Human mmCIF and SwissProt under the
passive policy remain in the database and are no longer reported. SwissProt
under the default disk I/O policy is still reported from the 0.9.0 session
(dataset `swissprot_500k_pdb`), because it was not measured again.

Compared with the 0.9.0 tables, zsasa batch times are 1-7% higher and single-file
times on small structures about 6 ms higher. That is the session and not the
release. Directly after the rerun, interleaved on the idle machine:

| Command | zsasa 0.9.0 | zsasa 0.12.1 |
| --- | --- | --- |
| E. coli batch, bitmask f32, 10 threads (3 x 5 runs) | 1.462 / 1.482 / 1.493 s | 1.466 / 1.505 / 1.500 s |
| Same, peak RSS | 47 MiB | 53-55 MiB |
| `calc`, AF-P49792-F10 PDB, f64, 10 threads (30 runs) | 18.9 ms | 18.8 ms |

The Human mmCIF step was measured twice. In the first run, the mmap variants
at 10 threads took 20.6 s (generic) and 18.6 s (AF-fast) in all three runs,
about 20% above 0.11.0, while the read variants matched 0.11.0, and Lahuta
slowed from run to run (17.0, 18.4, 23.4 s). Interleaved 0.11.0/0.12.1 runs
right after it gave equal times for both releases (mmap 17.0-17.7 s, read
17.0-17.6 s at 10 threads), so the step was run again with the same manifest
and run id on 2026-10-30. The rerun is the reported `v0_12_1_human_cif`
(10 threads: generic mmap 16.6 s, AF-fast mmap 15.0 s, Lahuta bitmask 15.6 s);
the first run is kept, not imported, as `results/full_rerun/v0_12_1_human_cif_first`.
In the rerun, generic mmap at 40 threads varied between runs (16.7, 20.1,
18.2 s); every other condition stayed within 3%. The cause of the slow first
run was not identified.

Comparators measured in this session also moved (E. coli, 10 threads: FreeSASA
batch +6%, RustSASA +8%, Lahuta bitmask -8%), so
ratios against rerun comparators carry no cross-session offset. Ratios against
the retained single-file comparators do. The higher batch peak RSS is a release
difference: since 0.11.0, batch reads each input file once instead of mapping it.
SwissProt under the passive policy is faster with 0.12.1 (bitmask f32 at 10
workers 344.1 s against 460.6 s for 0.9.0 and 398.1 s for 0.11.0); Lahuta took
433.5 s in this session against 487.9 s in October.
