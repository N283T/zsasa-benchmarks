# zsasa 0.9.0 benchmark refresh summary

Status as of 2026-07-16. Raw benchmark outputs and the populated DuckDB file are
local generated artifacts under `results/`; this document records the adopted
scope and the interpretation to preserve before regenerating figures and tables.

## Release comparison policy

- `zsasa` 0.6.0 is the last complete historical baseline.
- `zsasa` 0.9.0 is the current release-refresh target.
- The incomplete 0.7.0 results remain provenance-only and superseded.
- The 0.8.0 measurements are an intermediate development generation, not an
  active release comparison.
- Unchanged comparators are retained from their completed compatible suites
  instead of being rerun solely for the 0.9.0 refresh.

## Trajectory findings

The selective rerun removed the apparent large 0.9.0 regression
seen in the first trajectory refresh. At 10 threads, native 0.9.0 versus 0.6.0
is within a few percent for the adopted measurements:

- 5wvo: standard f32 `+1.1%`, standard f64 `-5.5%`, bitmask f32 `-1.2%`,
  and bitmask f64 `-2.1%` runtime change;
- 6sup: standard about `+1.8–1.9%` and bitmask about `+2.7–3.5%`;
- 5vz0: about `+1–2%`.

Positive runtime change means slower than 0.6.0; negative means faster. These
small differences should not be presented as a material regression.

The native trajectory path permits worker counts above the machine's 10 logical
CPUs. Relative to the adopted t10 medians, the median speedups across the 12
native standard/bitmask conditions were:

| Dataset | t20 vs t10 | t40 vs t10 | Approximate t40 runtime reduction |
| --- | ---: | ---: | ---: |
| 5wvo (1001 frames) | 1.050x | 1.098x | 8.9% |
| 6sup (1001 frames) | 1.026x | 1.039x | 3.8% |
| 5vz0 (10001 frames) | 1.048x | 1.065x | 6.1% |

t40 was fastest in all 5wvo and 6sup conditions and in 10 of 12 5vz0
conditions. The remaining two 5vz0 conditions differed from t20 by less than
0.04%. t10, t20, and t40 produced exactly identical per-frame total SASA values
for all 36 matched native conditions. Because each thread grid was collected in
a separate command session, use these values as practical scaling evidence, not
as an interleaved paired microbenchmark.

Bitmask `per-frame` LUT construction remains deliberately expensive: relative
to the single-LUT path it costs about 3.5x on 5wvo, 1.30x on 6sup, and 1.53x on
5vz0 at t10. The cycle LUT mode has little cost on the larger structures.

## Deliberately unadopted work

### E. coli AFDB mmCIF batch

`manifests/batch-ecoli-cif-zsasa-0.9.toml` is retained with
`status = "not_adopted"` and was not executed as formal 0.9.0 evidence. Human
AFDB mmCIF already covers parser selection, input I/O, and worker overcommit;
E. coli PDB already covers the smaller batch-throughput workload. The E. coli
mmCIF matrix would therefore duplicate adopted benchmark questions.

### Single-file worker overcommit

No t20/t40 single-file matrix is adopted. In zsasa 0.9.0, `calc --threads=N`
accepts values above the CPU count, but the shared calculation thread pool caps
the effective workers to `min(N, CPU count)`. On this 10-CPU system, t20 and t40
would both execute with 10 workers and would only repeat the t10 measurement.
